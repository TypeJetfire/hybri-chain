\chapter{HybriChain 在 Ollama 上的实现}
\label{chap:implementation}

上一章阐述了 HybriChain 面向任意多语言推理引擎的通用设计方法。本章以 Ollama 开源推理框架为具体靶点，说明各设计方案的具体实现。内容包括：第三章各节设计在 Ollama 上的对应实现、Ollama 工程特性带来的特殊挑战及其处理方案、以及完全源自 Ollama 自身架构特点的独门方法。

\section{Ollama 的工程特性}

Ollama 不是普通的单进程程序，它有三个在实现第三章追踪方案时必须处理的特点，理解这些特点是后续各节实现的前提。

\textbf{多进程架构。} Ollama 采用 daemon + runner 的双进程架构：daemon 进程负责接收外部 HTTP 请求，runner 子进程负责实际执行推理。两者通过 HTTP over TCP（127.0.0.1 随机端口）通信，而非传统的 Unix Domain Socket。daemon 和 runner 的 TID 编号空间各自独立，同一推理请求在两端的 TID 不同，这给跨进程缝合带来了根本性挑战。

\textbf{Go-CGO 混合层。} Ollama 的 API 层用 Go 编写，通过 CGO 调用底层的 llama.cpp C++ 推理库。Go 编译器生成的 CGO 桥接函数名并非直接对应源码中的函数名，而是包含哈希后缀，如 \texttt{\_cgo\_8aa400f2462b\_Cfunc\_llama\_decode}。这种名字无法与 llama.cpp 的 \texttt{llama\_decode} 直接对应，需要专门处理。

\textbf{Go 运行时与探针兼容性。} Go 1.17+ 的栈管理机制与 uretprobe 的 trampoline 实现不兼容，在 Go 函数上挂 uretprobe 会导致进程崩溃。因此第三章的 uprobe 策略在 Ollama 上需要做出调整：Go 层的事件采集依赖第三章设计的轻量级注入方案（见 4.5 节），C/C++ 层则直接挂载 uprobe/uretprobe。

\section{eBPF 追踪脚本的具体实现}

本节对应第三章 3.2 节的通用追踪方案在 Ollama 上的具体落地。

追踪脚本使用 bpftrace 语言编写，共两个文件：\texttt{trace\_ollama.bt} 用纯 tracepoint，轻量级，适合初步观测；\texttt{trace\_unified.bt} 用 uprobe + tracepoint，功能完整，是实际使用的追踪脚本。

\subsection{uprobe 挂载的具体函数}

Ollama 的推理引擎二进制（带调试信息的 ollama-debug）中，以下函数是第三章 3.2.2 节所定义的四类关键节点的具体对应：

\begin{enumerate}[(1)]
    \item \texttt{llama\_decode}：推理主循环，每生成一个 token 必然调用一次。挂载在函数入口（uprobe）和返回点（uretprobe），记录进入时刻和耗时差值，并输出调用栈（ustack，32 层深度）。
    \item \texttt{ggml\_backend\_sched\_graph\_compute\_async}：GGML 计算调度，不输出调用栈（GGML 内部函数太多，栈太深，价值不大）。
    \item \texttt{llama\_synchronize}：同步等待点。
    \item \texttt{llama\_sampler\_sample} 和 \texttt{common\_sampler\_csample}：采样函数，输出调用栈。
    \item \texttt{llama\_model\_load\_from\_file}：模型加载入口，记录模型加载的总耗时。
    \item \texttt{llama\_batch\_get\_one}：批处理函数。
\end{enumerate}

具体探针配置用算法~\ref{fig:uprobe-config} 描述。其中哈希表记录各线程的进入时刻，uretprobe 从哈希表取出时刻计算耗时后立即删除对应条目，避免哈希表无限增长：

\label{fig:uprobe-config}

\KwIn{binary path $B$；函数名 $F$；uprobe 事件流}
\KwOut{带耗时的 uprobe 事件行列表 $L$}

\BlankLine
\CommentSty{uprobe：函数入口}
\texttt{uprobe:$B$:"$F$"}
\BlankLine

输出格式中，\texttt{@UPROBE@} 是标记前缀，依次是函数名、纳秒时间戳、线程 ID、耗时（微秒），然后是调用栈帧，最后是 \texttt{@END@} 标记。

使用时要指定二进制文件路径（必须用带调试信息的 ollama-debug 版本，不能用 release 版本）。运行 bpftrace 追踪的命令格式为：\texttt{sudo\ bpftrace\ -o\ <输出文件>\ -B\ line\ <追踪脚本>}，其中 -o 指定输出文件，-B line 禁用输出缓冲。

\subsection{系统调用 tracepoint 的具体配置}

在内核系统调用层面，追踪以下 tracepoint：

\begin{itemize}
    \item \texttt{tracepoint:syscalls:sys\_enter/read/write/sendto/recvfrom/epoll\_wait}：I/O 操作
    \item \texttt{tracepoint:syscalls:sys\_enter/futex}：线程同步，关键的阻塞检测来源
    \item \texttt{tracepoint:syscalls:sys\_enter/exit\_mmap}：内存分配，KV Cache 的主要来源
    \item \texttt{tracepoint:syscalls:sys\_enter/exit\_clone3}：线程创建
\end{itemize}

futex 的处理稍有特殊：在入口记录时刻，在返回点计算耗时。如果耗时超过 500 微秒才输出事件（低于 500 微秒的 futex 等待是正常的锁操作，没有分析价值）。

read/write 的过滤条件是：返回值必须大于 0（失败的调用不记录），以此排除空读和失败调用。

\section{数据解析脚本的具体实现}

本节对应第三章 3.3 节的通用解析方案在 Ollama 上的具体落地。

trace\_unify.py 负责把 bpftrace 的原始文本输出转换成结构化的 JSON 事件列表。解析核心是状态机，以四种标记（\texttt{@TRACEID@}、\texttt{@UPROBE@}、\texttt{@SYSCALL@}、\texttt{@END@}）驱动状态转换，如算法~\ref{fig:parser-fsm} 所示：

trace\_unify.py 输出的 JSON 文件是后续所有处理脚本的数据来源，也是实验数据的基础。

\begin{algorithm}[H]
\caption{\texttt{bpftrace} 原始输出的解析状态机}
\label{fig:parser-fsm}
\DontPrintSemicolon
\KwIn{\texttt{bpftrace} 原始文本行列表 $L$}
\KwOut{事件对象列表 $E$，每个事件包含 $ts\_ns,\ tid,\ type,\ func,\ dur,\ stack,\ trace\_id,\ extra$}

\BlankLine
$\text{STATE} \leftarrow \text{IDLE}$\;
$\text{active\_trace\_id} \leftarrow \emptyset$ \tcp*[r]{tid $\rightarrow$ traceID 映射表}
$\text{cur\_stack} \leftarrow []$\;
$\text{cur\_func} \leftarrow \text{""}$\;
$\text{cur\_ts} \leftarrow 0$\;
$\text{cur\_tid} \leftarrow 0$\;
$\text{cur\_dur} \leftarrow 0$\;
$E \leftarrow []$

\BlankLine
\ForEach{$\text{line} \in L$}{
    \If{$\text{line} = \text{""}$} {$pass$ \tcp*{跳过空行}}
    \ElseIf{$\text{line}.\text{startsWith}("@TRACEID@") \}$}{
        $parts \leftarrow \text{line}.\text{split}()$\;
        $T \leftarrow \text{int}(parts[3])$\;
        $\text{active\_trace\_id}[T] \leftarrow parts[4]$
    }
    \ElseIf{$\text{line}.\text{startsWith}("@UPROBE@") \}$}{
        $parts \leftarrow \text{line}.\text{split}()$\;
        $\text{STATE} \leftarrow \text{BUILDING\_UPROBE}$\;
        $\text{cur\_func} \leftarrow parts[1]$\;
        $\text{cur\_ts} \leftarrow \text{int}(parts[2])$\;
        $\text{cur\_tid} \leftarrow \text{int}(parts[3])$\;
        $\text{cur\_dur} \leftarrow \text{int}(parts[4])$\;
        $\text{cur\_stack} \leftarrow []$
    }
    \ElseIf{$\text{line}.\text{startsWith}("@SYSCALL@") \}$}{
        $parts \leftarrow \text{line}.\text{split}()$\;
        $T \leftarrow \text{int}(parts[3])$\;
        $\text{extra} \leftarrow \text{parse\_params}(parts[4:])$\;
        $e \leftarrow \text{Event}(\text{cur\_ts},\ T,\ "syscall",$
        $parts[1],\ 0,\ [],\ \text{active\_trace\_id.get}(T,""),\ \text{extra})$\;
        $E.\text{append}(e)$
    }
    \ElseIf{$\text{line}.\text{startsWith}("@END@") \}$}{
        \If{$\text{STATE} = \text{BUILDING\_UPROBE}$}{
            $T \leftarrow \text{cur\_tid}$\;
            $\text{stack\_clean} \leftarrow [f \mid f \in \text{cur\_stack} \And \neg f.\text{startsWith}("0x")]$\;
            $\text{stack\_dem} \leftarrow \text{map}(\text{c++filt},\ \text{stack\_clean})$\;
            $e \leftarrow \text{Event}(\text{cur\_ts},\ T,\ "uprobe",$
            $\text{cur\_func},\ \text{cur\_dur},\ \text{stack\_dem},$
            $\text{active\_trace\_id.get}(T,""),\ \emptyset)$\;
            $E.\text{append}(e)$
        }
        $\text{STATE} \leftarrow \text{IDLE}$
    }
    \ElseIf{$\text{STATE} = \text{BUILDING\_UPROBE}$}{
        $\text{cur\_stack}.\text{append}(\text{line})$
    }
}

\BlankLine
\Return $\text{sort\_by\_ts}(E)$ \tcp*{按纳秒时间戳升序排序}
\end{algorithm}

\section{静态符号提取的具体实现}

本节对应第三章 3.6 节的通用分类体系在 Ollama 上的具体落地。

extract\_symbols.py 从 ollama-debug 二进制文件中提取函数符号，构建静态调用图 JSON。

用符号提取工具对带调试信息的二进制文件进行全局符号提取，工具的 -C 参数会自动 demangle C++ 符号，--defined-only 参数排除未定义符号，只保留有定义的函数。

过滤条件是：只保留符号类型为 T 或 t 的行（全局或本地符号），且符号名包含 llama、ggml、common、cgo、vocab 之一。这个过滤器会把大量 Go runtime 符号（如 sync.*、net.*）排除掉，只保留和推理相关的函数。

符号分类用算法~\ref{fig:classify-layer} 实现，按优先级从 L1 到 L8 依次检查前缀规则，命中即停止，保证每个符号唯一对应一个层次。\texttt{nm} 只能给出符号列表，调用关系由 KNOWN\_CALLS 手工建立（lla\_decode $\to$ \{ggml\_backend\_sched\_graph\_compute\_async, llama\_synchronize, ...\}）：

\begin{algorithm}[H]
\caption{函数符号层次分类算法}
\label{fig:classify-layer}
\DontPrintSemicolon
\KwIn{符号名 $s$}
\KwOut{层次标签 $L \in \{L1,\dots,L8\}$ 或 $\bot$（未分类）}

\BlankLine
\uIf{$\text{contains}(s, "\_cgo\_") \lor \text{contains}(s, "\_cgoexp\_")$}{
    \Return $L1$ \tcp*{ffi\_bridge}
}
\uElseIf{$\text{startsWith}(s, "llama\_") \land$
        $(\text{contains}(s, "decode") \lor \text{contains}(s, "model") \lor \text{contains}(s, "context"))$}{
    \Return $L2$ \tcp*{inference\_api}
}
\uElseIf{$\text{startsWith}(s, "llama\_") \land$
        $(\text{contains}(s, "batch") \lor \text{contains}(s, "sampler") \lor \text{contains}(s, "token"))$}{
    \Return $L3$ \tcp*{batch\_sampler}
}
\uElseIf{$\text{contains}(s, "sched") \lor \text{contains}(s, "graph\_compute")$}{
    \Return $L4$ \tcp*{sched\_compute}
}
\uElseIf{$(\text{startsWith}(s, "llama\_") \lor \text{startsWith}(s, "common\_"))
        \land \text{contains}(s, "backend")$}{
    \Return $L5$ \tcp*{backend}
}
\uElseIf{$\text{startsWith}(s, "ggml\_") \land \neg\text{contains}(s, "sched")
        \land \neg\text{contains}(s, "backend")$}{
    \Return $L6$ \tcp*{ops}
}
\uElseIf{$\text{contains}(s, "vocab") \lor \text{contains}(s, "tokenize")
        \lor \text{contains}(s, "detokenize") \lor \text{contains}(s, "piece")$}{
    \Return $L7$ \tcp*{vocab}
}
\uElseIf{$\text{contains}(s, "mmap") \lor \text{contains}(s, "munmap")
        \lor \text{contains}(s, "malloc") \lor \text{contains}(s, "buffer")$}{
    \Return $L8$ \tcp*{memory}
}
\Else{
    \Return $\bot$ \tcp*{不属于推理相关符号，跳过}
}
\end{algorithm}

\section{缝合模块的具体实现}

本节对应第三章 3.4 和 3.5 节的缝合算法在 Ollama 上的具体落地。

缝合模块由三个 Python 类协作完成：CGEdge（表示一条静态调用边）、CallGraph（加载静态调用图）、AnchorMatcher（做锚点匹配）、ConfidenceCalculator（计算置信度）。

AnchorMatcher 维护一个“等价映射表”，把各种格式的 CGO 函数名映射到 llama.cpp 的原始函数名，匹配策略按优先级递减执行（算法~\ref{fig:anchor-match}）。哈希值（8aa400f2462b）是 Ollama 版本的特征，和二进制文件强绑定。

\begin{algorithm}[H]
\caption{锚点函数名匹配算法}
\label{fig:anchor-match}
\DontPrintSemicolon
\KwIn{待匹配符号 $s$；CGO 等价映射表 $M_{\text{cgo}}$；静态符号集合 $S$}
\KwOut{目标语言层的规范化函数名 $s'$ 或 $\bot$}

\BlankLine
\uIf{$s \in M_{\text{cgo}}$}{
    \Return $M_{\text{cgo}}[s]$ \tcp*{优先级 1：CGO 等价表精确匹配}
}
\uElseIf{$s \in S$}{
    \Return $s$ \tcp*{优先级 2：静态符号表精确匹配}
}
\uElseIf{$\text{contains}(s, "\_cgoexp\_")$}{
    $s' \leftarrow \text{demangle}(s)$\;
    \If{$s' \in S$}{\Return $s'$} \tcp*{优先级 3：C++ demangle 后匹配}
}
\uElseIf{$|s| \ge 4$}{
    \ForEach{$f \in S$}{
        \If{$\text{contains}(f, s) \lor \text{contains}(s, f)$}{
            \Return $f$ \tcp*{优先级 4：子串宽松匹配}
        }
    }
}
\Return $\bot$ \tcp*{所有策略均未命中}
\end{algorithm}

具体步骤是：先把事件按 TID 分组，同一 TID 内时间间隔超过 50 毫秒的事件被认为是不同请求，分别构成独立的请求树。然后对每条静态边，检查它两端对应的函数是否在 $\ge 2$ 棵不同的请求树中共同出现。如果是，标记为 Confirmed；只在 1 棵请求树中共同出现，标记为 Inferred；都没出现，标记为 Unknown。

阈值选择依据是：Llama.cpp 的 token 生成速度大约是每秒 10\~30 个 token，相邻两次 \texttt{llama\_decode} 的间隔在 30\~100 毫秒之间。因此用 50 毫秒作为请求树的切分阈值——如果两次事件间隔超过 50 毫秒，说明它们属于不同的推理请求。

图~\ref{fig:confidence} 给出了置信度计算的整体流程：

\begin{figure}[H]
\begin{algorithm}[H]
\caption{置信度计算流程}
\label{fig:confidence}
\DontPrintSemicolon
\KwIn{静态调用图 $G=(V,E)$；动态事件列表 $E_{\text{dyn}}$；请求树构建函数 $\text{build\_trees}$；阈值 $T_{\text{gap}} = 50$ms}
\KwOut{每条边 $(u,v) \in E$ 的置信度标签 $C(u,v)$}

\BlankLine
$\text{trees} \leftarrow \text{build\_trees}(E_{\text{dyn}}, T_{\text{gap}})$ \tcp*{构建请求树}
\ForEach{$v \in V$}{
    $\text{tree\_set}[v] \leftarrow \emptyset$ \tcp*{$v$ 出现过的请求树集合}
}
\ForEach{$\text{tree} \in \text{trees}$}{
    \ForEach{$e \in \text{tree}.\text{events}$}{
        $\text{tree\_set}[e.\text{func}].\text{add}(\text{tree})$ \tcp*{记录每节点出现的请求树}
    }
}

\BlankLine
\ForEach{$(u,v) \in E$}{
    $n \leftarrow |\text{tree\_set}[u] \cap \text{tree\_set}[v]|$ \tcp*{两端共同出现的请求树数}
    \uIf{$n \ge 2$}{
        $C(u,v) \leftarrow \text{Confirmed}$ \tcp*{跨语言调用关系被多次独立观测}
    }
    \uElseIf{$n = 1$}{
        $C(u,v) \leftarrow \text{Inferred}$ \tcp*{只有间接证据}
    }
    \Else{
        $C(u,v) \leftarrow \text{Unknown}$ \tcp*{本次未观测到}
    }
}
\Return $C$
\end{algorithm}
\end{figure}

缝合完成后，调用缝合模块的命令行接口：\texttt{python3\ stitcher.py\ <事件文件>\ --graph\ <静态图>\ --summary\ --anchors\ --export\ <结果文件>}，即可完成跨语言调用链的缝合与导出。

输出内容包括：各置信等级的边数量统计、锚点命中详情（每个函数被命中多少次）、跨层调用关系列表、完整的缝合结果 JSON 文件。

\section{Ollama 独门方法：跨进程 traceID 注入}

Ollama 的 daemon + runner 双进程架构，使得同一推理请求在两端拥有完全不同的 TID 编号空间。这是第三章 3.5 节跨进程缝合方案在 Ollama 上必须解决的核心挑战。

Ollama 的双进程间通信走的是 HTTP over TCP（而非 UDS），这意味着进程间的 HTTP 连接本身不具备请求关联能力——daemon 侧发出的 HTTP POST 请求和 runner 侧接收到的请求，在 bpftrace 的 TID 视角下是毫不相干的两组线程。

针对这一 Ollama 特有的问题，HybriChain 的独门解决方案是：在 Ollama 代码中注入轻量级的跟踪函数和 traceID 传递机制，使 bpftrace uprobe 能够从 API 入口一路追踪到推理结束。该方案已实际修改 Ollama 源码，涉及三个文件，如算法~\ref{fig:traceid-inject} 所示。

\begin{algorithm}[H]
\caption{traceID 注入：三文件具体改动}
\label{fig:traceid-inject}
\DontPrintSemicolon
\SetKwBlock{ChangeA}{改动一（\texttt{llm/server.go}）：}{}
\SetKwBlock{ChangeB}{改动二（\texttt{server/routes.go}）：}{}
\SetKwBlock{ChangeC}{改动三（\texttt{runner/llamarunner/runner.go}）：}{}

\BlankLine
\ChangeA{
    \CommentSty{CompletionRequest 结构体新增字段：}
    $\text{TraceID} \leftarrow \text{string}$
    \BlankLine
    \CommentSty{daemon 向 runner 发起 HTTP 请求前：}
    $\text{serverReq.Header.Set}("X-Request-ID", \text{req.TraceID})$
}
\BlankLine
\ChangeB{
    \CommentSty{GenerateHandler / ChatHandler 推理入口处注入：}
    $\text{traceID} \leftarrow \text{uuid.NewString}()$ \tcp*{每次请求生成新 UUID}
    $\text{withTraceID}(\text{traceID},\ \lambda\ .\ \text{r.Completion}($
        $\text{llm.CompletionRequest}\{\text{TraceID}: \text{traceID},\dots\})$
}
\BlankLine
\ChangeC{
    \CommentSty{runner HTTP handler 入口处注入：}
    $\text{traceID} \leftarrow r.\text{Header.Get}("X-Request-ID")$
    $\text{withTraceID}(\text{traceID},\ \lambda\ .\ \text{runCompletion}(w, r, \text{req}))$
}
\end{algorithm}

其中 \texttt{withTraceID} 本身是空壳函数（仅执行闭包），性能影响为零。它存在的唯一目的是为 bpftrace 提供一个安全的 uprobe 挂载点来捕获 traceID——在 Go 运行时上不能挂 uretprobe，但 uprobe 是安全的。

\begin{algorithm}[H]
\caption{traceID 跨进程数据流}
\label{fig:traceid-flow}
\DontPrintSemicolon
\KwIn{一次推理请求}
\KwOut{带统一 traceID 的完整调用链事件}

\BlankLine
\CommentSty{daemon 侧：}
$\text{traceID} \leftarrow \text{uuid.NewString}()$ \tcp*{步骤 1：生成 UUID}
$\text{uprobe}("server.withTraceID", \text{traceID})$ \tcp*{bpftrace 捕获 daemon\_entry}
$\text{HTTP\_POST}(127.0.0.1:\text{runnerPort},\ \{$
    $\text{body}: \text{CompletionRequest},\ $
    $\text{header}: "X-Request-ID: \text{traceID}"$
$\})$

\BlankLine
\CommentSty{runner 侧：}
$\text{traceID}' \leftarrow r.\text{Header.Get}("X-Request-ID")$ \tcp*{步骤 3：从 header 取出}
$\text{uprobe}("llamarunner.withTraceID", \text{traceID}')$ \tcp*{bpftrace 捕获 runner\_entry}

\BlankLine
\CommentSty{缝合阶段：}
$\text{active\_trace\_id}[\text{tid}] \leftarrow \text{traceID}'$ \tcp*{更新映射表}
\CommentSty{后续所有 uprobe/syscall 事件继承该 traceID，按 traceID 分组归并}
\end{algorithm}

这一方案完全针对 Ollama 的多进程 HTTP 通信架构量身定制，其他推理引擎若采用不同的进程间通信机制，需要设计相应的 traceID 传递方式。

\section{异常检测规则的具体实现}

analyzer.py 实现了一个简单的规则引擎，遍历所有事件，对每个事件依次执行所有检测规则。

六条规则的具体实现逻辑与第三章 3.7 节的通用设计一致，Ollama 场景下的阈值设定参考了实测数据：

\textbf{futex\_block 规则。} 条件是 ev.type == “syscall”且 ev.func == “futex”且 ev.duration\_us > 1000（1 毫秒）。如果耗时超过 5000 微秒，级别是高风险；否则是中风险。输出字段包括耗时（毫秒）和 futex 操作码（op）。实测：Qwen2-0.5B 推理时最长的单次 futex 阻塞达到 15.2 秒。

\textbf{mmap\_size 规则。} 条件是 ev.func 匹配 mmap/mmap2 且从 extra 字典中取 length 字段。如果 length > 1GB，级别为 CRITICAL；如果 512MB < length <= 1GB，级别为 HIGH。实测基准：TinyLlama-1.1B KV Cache 约为 256MB，Qwen2-0.5B 约为 512MB。

\textbf{sensitive\_path 规则。} 条件是 ev.func == “openat”且打开的路径匹配敏感模式。敏感模式包括：blobs（中风险，Ollama 存放模型缓存的位置）、.gguf/.ggml（高风险）、server.json（低风险）、model.json（中风险）。路径字符串用 lower() 统一大小写后做子串匹配。

\textbf{read\_size\_anomaly 规则。} 条件是 ev.func == “read”且返回值（bytes 字段）> 128KB。一次正常的 read 通常是 512B（HTTPS buffer）或 4KB（页对齐），超过 128KB 说明在读大块数据，可能是 prompt 注入或异常数据传输。

\textbf{write\_non\_stdout 规则。} 条件是 ev.func 匹配 write/sendto/send 且 fd 不在标准描述符（0, 1, 2）范围内。如果 fd == 3（Ollama HTTP socket）且写入超过 1KB，级别是中风险，表示可能有推理结果外传。

\textbf{http\_socket\_read\_anomaly 规则。} 条件是 fd == 3 的 read 调用且 bytes > 1MB。Ollama HTTP socket 上的大块读入可能表示收到了大量输入数据，存在注入风险。

规则引擎的设计考虑是：每条规则独立运行，互不依赖，也不共享状态。这样做的好处是新规则的添加不影响现有逻辑，只需要把新函数加入规则列表即可。

输出格式是 JSON 报告，包含统计摘要（各类型告警数量、各风险级别告警数量）和详细告警列表（按风险等级降序排列的前 50 条）。

\section{完整追踪流程}

把以上所有模块串起来，完整的追踪流程如下：

第一步，准备带调试信息的二进制文件。需要从源码编译 Ollama，启用调试符号（Go 编译时加 -ldflags=“-s” 来保留符号表），生成 ollama-debug 文件。这是后续 bpftrace uprobe 挂载的前提——没有调试信息，bpftrace 无法定位函数地址。

第二步，运行追踪采集。依次启动 Ollama 服务、后台运行 bpftrace 追踪、发送推理请求，最后终止 bpftrace 进程完成采集。

第三步，数据解析和缝合。依次运行解析脚本将原始文本转换为结构化 JSON，运行缝合脚本完成跨语言调用链缝合，最后运行分析脚本生成异常报告。

第四步，查看结果。运行缝合脚本可查看缝合摘要与锚点统计；格式化查看 JSON 报告可获取异常告警详情。整个流程在实测中的运行数据：bpftrace 在 TinyLlama-1.1B 推理过程中采集了 25,329 行原始输出，经 trace\_unify.py 解析后得到 8,891 个有效事件，压缩比约 2.8 倍。Qwen2-0.5B 的压缩比约 2.1 倍。解析时间在毫秒级别，远快于推理过程本身。

缝合结果中，Confirmed 边全部落在 CGO 桥接层（Go $\rightarrow$ llama.cpp 边界），这正是 uprobe 探针挂载的位置。Inferred 边主要是 llama.cpp 内部的函数调用关系，这些函数在源码中存在，但本次采样的推理请求没有触发它们。Unknown 边是静态符号表里有但本次追踪完全没有观测到的函数，意味着它们对应的代码路径在本次采样期间没有被执行。

\section{本章小结}

本章给出了第三章各节设计方案在 Ollama 推理框架上的具体实现。

\S 4.1 分析了 Ollama 的三个工程特性（多进程架构、Go-CGO 混合层、Go 运行时与探针兼容性），说明这些特性如何影响后续各节的具体实现。

\S 4.2 给出了 bpftrace 追踪脚本的具体写法，包括 uprobe 挂载的 llama.cpp 函数列表（llama\_decode、ggml\_backend\_sched\_graph\_compute\_async 等）、tracepoint 的配置参数（futex 过滤阈值 500 微秒）、输出格式设计和二进制路径要求。

\S 4.3 说明了 trace\_unify.py 的解析状态机逻辑、调用栈 demangle 处理、无效行过滤规则。

\S 4.4 说明了 extract\_symbols.py 的符号提取和分类逻辑（按前缀匹配分为 8 层）、KNOWN\_CALLS 手工调用关系的建立方式，以及最终生成的静态调用图规模（4832 节点 / 52 边）。

\S 4.5 给出了缝合模块的置信度计算算法（按 TID 分组请求树，检查两端节点共同出现次数）和 AnchorMatcher 的等价映射表。

\S 4.6 是本章的独门方法：完全针对 Ollama 的多进程 HTTP 通信架构设计的 traceID 注入方案（withTraceID 函数 + X-Request-ID header + 双侧 uprobe），解决 daemon 和 runner TID 空间隔离的核心挑战。

\S 4.7 实现了六条异常检测规则，说明每条规则的触发条件、阈值选择依据（参考实测数据）和风险级别判定逻辑。
