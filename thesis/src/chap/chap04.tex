\chapter{HybriChain 在 Ollama 上的实现}
\label{chap:implementation}

上一章阐述了 HybriChain 面向任意多语言推理引擎的通用设计方法。本章以 Ollama 开源推理框架为具体靶点，说明各设计方案的具体实现。内容包括：第三章各节设计在 Ollama 上的对应实现、Ollama 工程特性带来的特殊挑战及其处理方案、以及完全源自 Ollama 自身架构特点的特有方法。

\section{Ollama 的工程特性}

Ollama 不是普通的单进程程序，它有三个在实现第三章追踪方案时必须处理的特点，理解这些特点是后续各节实现的前提。

多进程架构。Ollama 采用 daemon + runner 的双进程架构：daemon 进程负责接收外部 HTTP 请求，runner 子进程负责实际执行推理。两者通过 HTTP over TCP（127.0.0.1 随机端口）通信，而非传统的 Unix Domain Socket。daemon 和 runner 的 TID 编号空间各自独立，同一推理请求在两端的 TID 不同，这给跨进程缝合带来了根本性挑战。

Go-CGO 混合层。Ollama 的 API 层用 Go 编写，通过 CGO 调用底层的 llama.cpp C++ 推理库。Go 编译器生成的 CGO 桥接函数名并非直接对应源码中的函数名，而是包含哈希后缀，如 \texttt{\_cgo\_8aa400f2462b\_Cfunc\_llama\_decode}。这种名字无法与 llama.cpp 的 \texttt{llama\_decode} 直接对应，需要专门处理。

Go 运行时与探针兼容性。Go 1.17+ 的栈管理机制与 uretprobe 的 trampoline 实现不兼容，在 Go 函数上挂 uretprobe 会导致进程崩溃。因此第三章的 uprobe 策略在 Ollama 上需要做出调整：Go 层的事件采集依赖第三章设计的轻量级注入方案，C/C++ 层则直接挂载 uprobe/uretprobe。

\section{eBPF 追踪脚本的具体实现}

本节对应第三章通用追踪方案在 Ollama 上的具体落地。

追踪脚本使用 bpftrace 语言编写，共两个文件：\texttt{trace\_ollama.bt} 用纯 tracepoint，轻量级，适合初步观测；\texttt{trace\_unified.bt} 用 uprobe + tracepoint，功能完整，是实际使用的追踪脚本。

\subsection{uprobe 挂载的具体函数}

Ollama 的推理引擎二进制（带调试信息的 ollama-debug）中，以下函数是第三章所定义的四类关键节点的具体对应：

\begin{enumerate}[(1)]
    \item \texttt{llama\_decode}：推理主循环，每生成一个 token 必然调用一次。挂载在函数入口（uprobe）和返回点（uretprobe），记录进入时刻和耗时差值，并输出调用栈（ustack，32 层深度）。
    \item \texttt{ggml\_backend\_sched\_graph\_compute\_async}：GGML 计算调度，不输出调用栈（GGML 内部函数太多，栈太深，价值不大）。
    \item \texttt{llama\_synchronize}：同步等待点。
    \item \texttt{llama\_sampler\_sample} 和 \texttt{common\_sampler\_csample}：采样函数，输出调用栈。
    \item \texttt{llama\_model\_load\_from\_file}：模型加载入口，记录模型加载的总耗时。
    \item \texttt{llama\_batch\_get\_one}：批处理函数。
\end{enumerate}

具体探针配置用算法~\ref{fig:uprobe-config} 描述。其中哈希表记录各线程的进入时刻，uretprobe 从哈希表取出时刻计算耗时后立即删除对应条目，避免哈希表无限增长：

输出格式中，\texttt{@UPROBE@} 是标记前缀，依次是函数名、纳秒时间戳、线程 ID、耗时（微秒），然后是调用栈帧，最后是 \texttt{@END@} 标记。

使用时要指定带调试信息的二进制文件路径（不能用 release 版本）。运行 bpftrace 追踪时，通过 -o 参数指定输出文件路径，-B line 参数禁用输出缓冲以实时写入。

\subsection{系统调用 tracepoint 的具体配置}

在内核系统调用层面，追踪以下 tracepoint：

\begin{itemize}
    \item \texttt{tracepoint:syscalls:sys\_enter/read/write/sendto/recvfrom/epoll\_wait}：I/O 操作
    \item \texttt{tracepoint:syscalls:sys\_enter/futex}：线程同步，关键的阻塞检测来源
    \item \texttt{tracepoint:syscalls:sys\_enter/exit\_mmap}：内存分配，KV Cache 的主要来源
    \item \texttt{tracepoint:syscalls:sys\_enter/exit\_clone3}：线程创建
\end{itemize}

futex 的处理稍有特殊：在入口记录时刻，在返回点计算耗时。如果耗时超过 500 微秒才输出事件（低于 500 微秒的 futex 等待是正常的锁操作，没有分析价值）。

read/write 的过滤条件是：返回值必须大于 0（失败的调用不记录），以此排除空读和失败调用。

\section{数据解析脚本的具体实现}

本节对应第三章通用解析方案在 Ollama 上的具体落地。

trace\_unify.py 负责把 bpftrace 的原始文本输出转换成结构化的 JSON 事件列表。解析核心是状态机，以四种标记（\texttt{@TRACEID@}、\texttt{@UPROBE@}、\texttt{@SYSCALL@}、\texttt{@END@}）驱动状态转换。

trace\_unify.py 输出的 JSON 文件是后续所有处理脚本的数据来源，也是实验数据的基础。

解析脚本的核心是一个状态机，bpftrace 输出的每行文本根据前缀标记进入不同状态。状态机维护四个内部变量：当前状态（IDLE 或 BUILDING\_UPROBE）、线程 traceID 映射表、当前函数的上下文信息、调用栈累积列表。

处理流程如下：遇到 @TRACEID@ 行时，从第 4 和第 5 个字段提取线程 ID 和 traceID，更新映射表；遇到 @UPROBE@ 行时，切换为 BUILDING\_UPROBE 状态，提取函数名、时间戳、线程 ID、耗时并存入 	exttt{cur\_*} 变量；此后该状态下的每一行文本都作为调用栈帧累积；遇到 @SYSCALL@ 行时，直接构造一个 syscall 类型事件并追加到结果列表；遇到 @END@ 行时，若当前状态为 BUILDING\_UPROBE，则用累积的调用栈帧构造 uprobe 类型事件，最后切换回 IDLE 状态。调用栈帧中以 0x 开头的内存地址被过滤掉，不保留无分析价值的地址信息。全部解析完成后，按纳秒时间戳升序排序输出事件列表。

\section{静态符号提取的具体实现}

本节对应第三章通用分类体系在 Ollama 上的具体落地。

extract\_symbols.py 从 ollama-debug 二进制文件中提取函数符号，构建静态调用图 JSON。

用符号提取工具对带调试信息的二进制文件进行全局符号提取，工具的 -C 参数会自动 demangle C++ 符号，--defined-only 参数排除未定义符号，只保留有定义的函数。

过滤条件是：只保留符号类型为 T 或 t 的行（全局或本地符号），且符号名包含 llama、ggml、common、cgo、vocab 之一。这个过滤器会把大量 Go runtime 符号（如 sync.*、net.*）排除掉，只保留和推理相关的函数。

符号分类按优先级从 L1 到 L8 依次检查前缀规则，命中即停止，保证每个符号唯一对应一个层次。\texttt{nm} 只能给出符号列表，调用关系由 KNOWN\_CALLS 手工建立（lla\_decode $\to$ \{ggml\_backend\_sched\_graph\_compute\_async, llama\_synchronize, ...\}）。八级层次分别是：L1 为 FFI 桥接层（符号名含 \_cgo\_ 或 \_cgoexp\_），L2 为推理 API 层（前缀 llama\_ 且含 decode / model / context），L3 为批采样层（前缀 llama\_ 且含 batch / sampler / token），L4 为调度计算层（符号含 sched 或 graph\_compute），L5 为推理后端层（前缀 llama\_ 或 common\_ 且含 backend），L6 为算子层（前缀 ggml\_ 且不含 sched/backend），L7 为词表层（含 vocab / tokenize / detokenize / piece），L8 为内存管理层（含 mmap / munmap / malloc / buffer）。不属于上述任一层次的符号标记为 $\bot$ 跳过。最终输出静态调用图 JSON。

\section{缝合模块的具体实现}

本节对应第三章缝合算法在 Ollama 上的具体落地。

缝合模块由三个 Python 类协作完成：CGEdge（表示一条静态调用边）、CallGraph（加载静态调用图）、AnchorMatcher（做锚点匹配）、ConfidenceCalculator（计算置信度）。

AnchorMatcher 维护一个“等价映射表”，把各种格式的 CGO 函数名映射到 llama.cpp 的原始函数名，匹配策略按优先级递减执行（算法~\ref{fig:anchor-match}）。哈希值（8aa400f2462b）是 Ollama 版本的特征，和二进制文件强绑定。

解析脚本的核心是一个状态机，bpftrace 输出的每行文本根据前缀标记进入不同状态。状态机维护四个内部变量：当前状态（IDLE 或 BUILDING\_UPROBE）、线程 traceID 映射表、当前函数的上下文信息、调用栈累积列表。

处理流程如下：遇到 @TRACEID@ 行时，从第 4 和第 5 个字段提取线程 ID 和 traceID，更新映射表；遇到 @UPROBE@ 行时，切换为 BUILDING\_UPROBE 状态，提取函数名、时间戳、线程 ID、耗时并存入 	exttt{cur\_*} 变量；此后该状态下的每一行文本都作为调用栈帧累积；遇到 @SYSCALL@ 行时，直接构造一个 syscall 类型事件并追加到结果列表；遇到 @END@ 行时，若当前状态为 BUILDING\_UPROBE，则用累积的调用栈帧构造 uprobe 类型事件，最后切换回 IDLE 状态。调用栈帧中以 0x 开头的内存地址被过滤掉，不保留无分析价值的地址信息。全部解析完成后，按纳秒时间戳升序排序输出事件列表。

具体步骤是：先把事件按 TID 分组，同一 TID 内时间间隔超过 50 毫秒的事件被认为是不同请求，分别构成独立的请求树。然后对每条静态边，检查它两端对应的函数是否在 $\ge 2$ 棵不同的请求树中共同出现。如果是，标记为 Confirmed；只在 1 棵请求树中共同出现，标记为 Inferred；都没出现，标记为 Unknown。

阈值选择依据是：Llama.cpp 的 token 生成速度大约是每秒 10\~30 个 token，相邻两次 \texttt{llama\_decode} 的间隔在 30\~100 毫秒之间。因此用 50 毫秒作为请求树的切分阈值——如果两次事件间隔超过 50 毫秒，说明它们属于不同的推理请求。

图~\ref{fig:confidence} 给出了置信度计算的整体流程：

\begin{figure}[H]
\begin{algorithm}[H]
\caption{置信度计算流程}
\label{fig:confidence}
\DontPrintSemicolon
\KwIn{静态调用图 $G=(V,E)$；动态事件列表 $E_{\text{dyn}}$；请求树构建函数 $\text{build\_trees}$；阈值 $T_{\text{gap}} = 50$ms}
\KwOut{每条边 $(u,v) \in E$ 的置信度标签 $C(u,v)$}

\BlankLine
$\text{trees} \leftarrow \text{build\_trees}(E_{\text{dyn}}, T_{\text{gap}})$ \tcp*{构建请求树}
\ForEach{$v \in V$}{
    $\text{tree\_set}[v] \leftarrow \emptyset$ \tcp*{$v$ 出现过的请求树集合}
}
\ForEach{$\text{tree} \in \text{trees}$}{
    \ForEach{$e \in \text{tree}.\text{events}$}{
        $\text{tree\_set}[e.\text{func}].\text{add}(\text{tree})$ \tcp*{记录每节点出现的请求树}
    }
}

\BlankLine
\ForEach{$(u,v) \in E$}{
    $n \leftarrow |\text{tree\_set}[u] \cap \text{tree\_set}[v]|$ \tcp*{两端共同出现的请求树数}
    \uIf{$n \ge 2$}{
        $C(u,v) \leftarrow \text{Confirmed}$ \tcp*{跨语言调用关系被多次独立观测}
    }
    \uElseIf{$n = 1$}{
        $C(u,v) \leftarrow \text{Inferred}$ \tcp*{只有间接证据}
    }
    \Else{
        $C(u,v) \leftarrow \text{Unknown}$ \tcp*{本次未观测到}
    }
}

\end{algorithm}

缝合完成后，运行缝合模块：传入事件文件与静态调用图，即可完成跨语言调用链的缝合与导出，同时输出 Confirmed / Inferred / Unknown 边的统计摘要。

输出内容包括：各置信等级的边数量统计、锚点命中详情（每个函数被命中多少次）、跨层调用关系列表、完整的缝合结果 JSON 文件。

\section{跨进程 traceID 注入}

Ollama 的 daemon + runner 双进程架构，使得同一推理请求在两端拥有完全不同的 TID 编号空间。这是跨进程缝合方案在 Ollama 上必须解决的核心挑战。

Ollama 的双进程间通信走的是 HTTP over TCP（而非 UDS），这意味着进程间的 HTTP 连接本身不具备请求关联能力——daemon 侧发出的 HTTP POST 请求和 runner 侧接收到的请求，在 bpftrace 的 TID 视角下是毫不相干的两组线程。

针对这一 Ollama 的问题，HybriChain 的解决方案是：在 Ollama 代码中注入轻量级的跟踪函数和 traceID 传递机制，使 bpftrace uprobe 能够从 API 入口一路追踪到推理结束。该方案已实际修改 Ollama 源码，涉及三个文件，如算法~\ref{fig:traceid-inject} 所示。

\section{异常检测规则的具体实现}

analyzer.py 实现了一个简单的规则引擎，遍历所有事件，对每个事件依次执行所有检测规则。

六条规则的具体实现逻辑与第三章通用设计一致，Ollama 场景下的阈值设定参考了实测数据：

futex\_block 规则。 条件是 ev.type == “syscall”且 ev.func == “futex”且 ev.duration\_us > 1000（1 毫秒）。如果耗时超过 5000 微秒，级别是高风险；否则是中风险。输出字段包括耗时（毫秒）和 futex 操作码（op）。实测：Qwen2-0.5B 推理时最长的单次 futex 阻塞达到 15.2 秒。

mmap\_size 规则。 条件是 ev.func 匹配 mmap/mmap2 且从 extra 字典中取 length 字段。如果 length > 1GB，级别为 CRITICAL；如果 512MB < length <= 1GB，级别为 HIGH。实测基准：TinyLlama-1.1B KV Cache 约为 256MB，Qwen2-0.5B 约为 512MB。

sensitive\_path 规则。 条件是 ev.func == “openat”且打开的路径匹配敏感模式。敏感模式包括：blobs（中风险，Ollama 存放模型缓存的位置）、.gguf/.ggml（高风险）、server.json（低风险）、model.json（中风险）。路径字符串用 lower() 统一大小写后做子串匹配。

read\_size\_anomaly 规则。 条件是 ev.func == “read”且返回值（bytes 字段）> 128KB。一次正常的 read 通常是 512B（HTTPS buffer）或 4KB（页对齐），超过 128KB 说明在读大块数据，可能是 prompt 注入或异常数据传输。

write\_non\_stdout 规则。 条件是 ev.func 匹配 write/sendto/send 且 fd 不在标准描述符（0, 1, 2）范围内。如果 fd == 3（Ollama HTTP socket）且写入超过 1KB，级别是中风险，表示可能有推理结果外传。

http\_socket\_read\_anomaly 规则。 条件是 fd == 3 的 read 调用且 bytes > 1MB。Ollama HTTP socket 上的大块读入可能表示收到了大量输入数据，存在注入风险。

规则引擎的设计考虑是：每条规则独立运行，互不依赖，也不共享状态。这样做的好处是新规则的添加不影响现有逻辑，只需要把新函数加入规则列表即可。

输出格式是 JSON 报告，包含统计摘要（各类型告警数量、各风险级别告警数量）和详细告警列表（按风险等级降序排列的前 50 条）。

\section{完整追踪流程}

算法~\ref{fig:trace-pipeline} 给出了完整追踪流程的步骤。

\begin{algorithm}[H]
\caption{追踪流程算法}
\label{fig:trace-pipeline}
\KwIn{待追踪推理引擎}
\KwOut{跨语言调用链 JSON，异常报告 JSON}

\BlankLine
\tcp{第一步：准备阶段}
$bin\_dbg \leftarrow$ 编译带调试符号的推理引擎二进制\;
$static\_graph \leftarrow$ 符号提取工具解析 $bin\_dbg$，生成静态调用图\;

\BlankLine
\tcp{第二步：追踪采集}
$pid \leftarrow$ 启动推理引擎服务\;
$bt\_pid \leftarrow$ 后台启动 bpftrace 追踪，绑定 $bin\_dbg$\;
向推理接口发送测试 prompt 请求\;
终止 bpftrace 进程，输出原始追踪文件 $F_{raw}$\;

\BlankLine
\tcp{第三步：数据解析}
$E \leftarrow$ 解析器将 $F_{raw}$ 转换为结构化事件列表\;
$G_s \leftarrow$ 缝合模块加载静态调用图 $static\_graph$\;
$G_c \leftarrow$ 缝合模块对事件列表 $E$ 执行跨语言调用链缝合\;
$R \leftarrow$ 分析模块对 $E$ 执行六条异常检测规则\;

\BlankLine
\tcp{第四步：结果输出}
输出缝合摘要（Confirmed / Inferred / Unknown 边统计）\;
输出异常告警报告（按风险级别降序）\;

\Return $G_c$, $R$
\end{algorithm}

实测数据：bpftrace 在 TinyLlama-1.1B 推理过程中采集了 25,329 行原始输出，经解析后得到 8,891 个有效事件，压缩比约 2.8 倍。Qwen2-0.5B 的压缩比约 2.1 倍。缝合结果中，Confirmed 边全部落在 CGO 桥接层（Go $
ightarrow$ llama.cpp 边界），这正是 uprobe 探针挂载的位置。Inferred 边主要是 llama.cpp 内部的函数调用关系，这些函数在源码中存在，但本次采样的推理请求没有触发它们。Unknown 边是静态符号表里有但本次追踪完全没有观测到的函数，意味着它们对应的代码路径在本次采样期间没有被执行。

\section{本章小结}

本章以 Ollama 开源推理框架为靶点，完整实现了第三章设计的 HybriChain 调用链追踪方案。Ollama 的多进程架构（daemon 与 runner 分离）和 Go/CGO/C++ 异构语言层给追踪带来了一系列特殊挑战：Go 运行时不支持 uretprobe、CGO 边界处的符号不匹配、daemon 与 runner 之间 TID 空间完全隔离。针对这些问题，本章分别给出了对应的工程解决方案：用 uprobe 替代 uretprobe 以保证探针兼容性、用五级锚点加哈希等价映射实现 CGO 边界处的符号匹配、用注入轻量级 traceID 机制实现跨进程的请求关联。整体追踪流程经端到端实测验证，在 TinyLlama-1.1B 与 Qwen2-0.5B 两个模型上均能正确采集事件并完成调用链缝合，为下一章的系统评估提供了完整的实验数据。
