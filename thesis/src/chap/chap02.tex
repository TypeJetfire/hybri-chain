\chapter{相关技术综述}
\label{chap:background}

本章介绍论文涉及的核心技术，包括大模型推理引擎的架构特点、eBPF 追踪技术、跨语言程序分析方法、以及动态二进制插桩工具。

\section{大模型推理引擎的架构}

\subsection{内存墙问题}

大模型参数多，这是最直接的问题。GPT-2 有 1.5B 参数，存下来大约 3GB；LLaMA-7B 存下来 14GB。这些参数在推理时需要不断从内存里读出来用。问题在于，GPU 的计算速度比内存带宽增长得快得多——算力每年能翻倍，但内存带宽每年只能增长大约 30\%。这意味着 GPU 有大量时间在等数据，而不是在做计算。这个现象叫"内存墙"（Memory Wall）。

为了让模型能在有限内存里跑起来，开发者做了各种优化。llama.cpp 用的整数量化（INT4/INT8）是最常见的方法——把每个参数从 16 位浮点数压缩到 4 位整数，内存占用直接降四分之一，精度损失在可接受范围内。PagedAttention 是另一个关键优化，它借鉴了操作系统的虚拟内存分页思想，把 KV Cache 切成固定大小的块，按需分配，显著减少了内存碎片。

但这些优化让代码变复杂了。PagedAttention 要管理几千个内存块，量化要在线做 INT4 解压缩，多级缓存要有替换策略——这些都增加了推理引擎内部的复杂性。

\subsection{Ollama 的三层架构}

Ollama 是这两年用得比较多的开源推理框架。它的架构特点是 Go-CGO-C++ 三层混合：

最上层是 Go HTTP Handler，负责接收 API 请求。Ollama 提供 REST API，POST 一个 JSON 过去就能生成文本。Go 这一层做请求解析、参数校验、调用链路的控制。

中间层是 CGO 桥接。Go 不能直接调用 C++，中间要靠 CGO 来做桥接。Go 代码里写一句 \texttt{C.llama\_decode}，Go 编译器就会生成一个 CGO 桥接函数，这个函数再调用真正的 llama.cpp 函数。问题是，Go 编译器生成的 CGO 函数名不是 \texttt{cgo:warning} 这种可读格式，而是 \texttt{\_cgo\_8aa400f2462b\_Cfunc\_llama\_decode} 这种带哈希后缀的名字。

最底层是 llama.cpp C++ 层，这是实际做推理的地方。\texttt{llama\_decode} 是主循环入口，每生成一个 token 就会调用一次。底层调用 ggml 库做矩阵运算，用系统调用（mmap/futex/clone3）来管理内存和线程。

整个调用链是这样的：HTTP 请求 → Go Handler → CGO 桥接函数 → llama.cpp 函数 → ggml 算子 → 内核系统调用。这条链横跨四层，完全不同的语言和运行环境，想看清楚里面发生了什么，并不容易。

\subsection{推理引擎的安全问题}

推理引擎暴露的安全问题主要和 API 与数据处理有关。

TorchServe 是 PyTorch 的模型部署工具，提供 REST API 来加载和运行模型。它的早期版本在反序列化模型文件时存在漏洞（CVE-2023-43654），攻击者可以上传构造好的恶意 YAML 文件来执行任意命令。

Ollama 在 2024 年被 Wiz 安全团队发现路径穿越漏洞（CVE-2024-37032）。Ollama 的 API 接受一个 digest 参数来验证模型文件的完整性，但这个参数的校验不够严格，攻击者可以用路径穿越符（\texttt{../}）来读取服务器上的任意文件。

这些漏洞的共同特点是：问题出在高层 API 和底层文件系统之间的数据流通路上，但现有的安全工具无法追踪数据在这条通路上具体经过了哪些函数、触发了哪些系统调用。

\section{eBPF 技术}

eBPF（extended Berkeley Packet Filter）是一个内核里的虚拟机，可以安全地运行用户自定义的程序。

它的基本工作方式是：用户写一段 C 语言的程序（或者用 bpftrace 这样的高级语言），这段程序经过内核的 Verifier 检查（确认它不会死循环、不会越界访问），然后被 JIT 编译成本地指令，加载到内核里执行。整个过程不需要修改内核代码，也不需要重启系统。

eBPF 的主要用途是追踪和监控。和 strace 相比，strace 靠 ptrace 实现，每次系统调用要两次上下文切换（用户→内核→用户），开销很大；eBPF 程序直接在内核里执行，没有额外的上下文切换开销。和 DBI 工具（如 Pin、Valgrind）相比，eBPF 的程序是独立的，不需要修改被追踪程序的代码，也不会显著拖慢程序。

eBPF 有几种追踪方式：

uprobe 是在用户态函数上挂探针，类似于在某个函数的入口和返回点插入回调。uretprobe 是 uprobe 的返回版本，可以拿到函数执行的耗时。但要注意，Go 1.17+ 的 runtime 实现和 uretprobe 有兼容问题，在 Go 函数上挂 uretprobe 会破坏栈帧结构，可能导致进程崩溃。稳妥的做法是只在 C/C++ 函数上挂探针。

tracepoint 是在内核的固定位置挂探针。Linux 内核在每个系统调用的入口和返回点都预留了 tracepoint，不需要知道函数地址，直接按名字attach 就行。tracepoint 的开销比 uprobe 还低，因为它是内核自己提供的接口。

perf 是 Linux 自带的性能分析工具，底层也用 eBPF。它适合做 CPU 热点分析，但输出格式不太方便程序解析。bpftrace 是更高级的工具，用类似 awk 的语法写追踪脚本，输出是文本格式，便于后续用 Python 脚本处理。

eBPF 的局限是：它本身只是一个数据通道，不理解被追踪程序的业务语义。eBPF 可以告诉你"某个系统调用发生了"，但不能告诉你"这个系统调用对应的是推理过程的哪一步"。要把 eBPF 用好，需要配合业务逻辑的理解。

还有一些研究把 eBPF 用到了更专门的场景。ProfInfer 用 uprobe 加硬件性能计数器（PMC）来分析神经网络算子的缓存行为，能精确到 L3 缓存未命中的粒度。但这种专一化的方案不包含跨语言语义，对 API 级别的安全分析没有帮助。

\section{跨语言程序分析}

多语言混合编程是现在大型项目的常态。Python 写高层逻辑，C/C++ 写性能关键代码，Go 写网络服务——这种组合很常见，但给程序分析带来了麻烦。

不同语言之间的调用关系，叫跨语言调用链（CrosS-Language Call Chain）。在单语言程序里，控制流是连续的，可以用 CFG（控制流图）来描述。但跨语言程序里，Go 层的函数和 C++ 层的函数在编译后各自独立，靠 CGO 桥接函数来连接——传统的 CFG 分析在语言边界处就断了。

Go 语言和 C/C++ 的互操作靠 CGO。CGO 的工作方式是：Go 代码里写 \texttt{C.foo()}，Go 编译器就会生成一个桥接函数，这个函数负责把 Go 的数据格式转成 C 的格式，调用真正的 C 函数，然后把返回值再转回 Go 的格式。问题是，Go 编译器生成的桥接函数名包含哈希后缀，无法直接还原成原始的 Go 函数名。

从二进制里提取符号，用 \texttt{nm} 工具就行。但 \texttt{nm} 只能给出函数列表，不能告诉你哪个函数调用了哪个函数——调用关系要从源码分析或者调用栈里提取。

还有一些静态分析工具尝试处理跨语言问题。比如 POLYCALL 把不同语言转成 WebAssembly 中间表示，然后在这个统一的中间层上做分析。效果不错，但前提是语言能编译到 Wasm——很多 C/C++ 项目没有 Wasm 支持，做不到。

动态分析不受编译目标限制。可以在运行时插桩，记录函数之间的调用关系。但动态分析要求程序实际运行起来，而推理引擎的调用路径可能很长、很动态，不一定每次都走同一条路。

CGO 还有个特殊问题：Go 编译器对每个 CGO 函数的哈希后缀是基于包路径和函数签名生成的。只要代码改一点，哈希值就变了。这导致符号表里的 CGO 函数名和源码里看到的不一样，必须做等价映射才能关联起来。

\section{动态二进制插桩}

动态二进制插桩（DBI）是在程序运行时插入额外代码的技术。相比静态插桩（修改源码重新编译），DBI 不需要源码，也不需要重新编译程序。

DynamoRIO 是一个主流的 DBI 框架。它的工作方式是：把被追踪程序的代码复制到一块"代码缓存"里，在复制过程中插入额外的分析代码，然后执行修改后的副本。这样做的好处是不需要修改原始程序，而且代码缓存可以复用，性能比每次都插桩要好。

DBI 可以做到很细的粒度。Valgrind 的 Memcheck 可以检测出内存未初始化使用、越界访问、内存泄漏等 bug，精度很高。代价是性能下降几十倍——Memcheck 要为每个内存访问维护影子内存来记录访问状态，这个开销非常大。

对于推理引擎来说，几十倍的性能下降是不可接受的。llama.cpp 在 CPU 上跑 1B 参数模型，每秒能生成几十个 token；如果用 Memcheck 跟踪，可能每秒只能生成 1 个 token，交互体验完全没法用。

总结一下各技术的取舍：eBPF 适合做低开销的系统级追踪，但不理解业务语义；静态符号分析能告诉你程序"可能"长什么样，但不知道"实际"怎么跑；DBI 太重，不适合生产环境；跨语言分析工具各有局限，没有一个能直接解决"把跨语言调用链看清楚"这个问题。

这就是本文要填补的空白：用一个动静结合的方法，把 eBPF 的低开销追踪、静态符号的语义分类、和跨语言调用链的缝合组合起来，在不影响推理引擎运行的前提下，把完整的调用链看清楚。

\section{本章小结}

本章介绍了涉及的核心技术：大模型推理引擎的 Go-CGO-C++ 三层混合架构、eBPF 的追踪原理和局限性、跨语言程序分析的主要挑战、以及动态二进制插桩工具的能力和开销。

现有技术各有不足：eBPF 本身是数据通道，不理解 AI 框架的内部语义；静态分析不知道运行时实际情况；DBI 性能开销太大；跨语言工具依赖编译目标或缺少运行时信息。

HybriChain 的思路是把 eBPF 追踪（拿到运行时事实）和静态符号分类（赋予语义层次）结合起来，用缝合算法把它们合成为可理解的跨语言调用链。下一章开始介绍系统设计。
