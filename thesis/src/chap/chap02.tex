\chapter{相关技术综述}
\label{chap:background}

本章介绍本文涉及的核心技术背景，包括大语言模型推理引擎的系统架构、eBPF 追踪技术的原理与特点、跨语言程序分析的主要方法以及动态二进制插桩体系的工作方式。

\section{大语言模型推理引擎的架构}

\subsection{推理过程中的内存瓶颈}

大语言模型的参数量巨大，GPT-2 约 15 亿参数，存储需要约 3GB 内存；LLaMA-7B 存储需要约 14GB。在推理过程中，这些参数需要反复从内存中读取使用。然而，GPU 的计算能力增长速度快于内存带宽增长，处理器在大量时间处于等待数据的状态，这一现象称为"内存墙"问题。

为缓解内存瓶颈，工业界提出了多种优化方案。整数量化技术将参数从 16 位浮点数压缩至 4 位或 8 位整数表示，内存占用可降低至原来的四分之一到八分之一，精度损失通常在可接受范围内。PagedAttention 机制借鉴操作系统虚拟内存的分页管理思想，将 KV Cache 划分为固定大小的块进行管理，避免了连续大块内存分配带来的碎片化问题。此外，多级缓存策略将热点数据保留在高带宽内存中，以减少对主存的访问次数。

这些优化措施在提升性能的同时，也使得推理引擎的系统架构日趋复杂，普遍采用了多语言混合编程模式。

\subsection{Ollama 的三层混合架构}

Ollama 是一款广泛使用的开源推理框架，其内部架构可分为三个层次。

最上层为 Go HTTP Handler 层，负责接收外部 API 请求并调用下层接口。Ollama 通过 REST API 提供模型推理服务，POST 请求携带 JSON 格式的推理参数，由 Go 侧负责解析和路由。

中间层为 CGO 桥接层。Go 语言本身不支持直接调用 C/C++ 代码，需要通过 CGO 机制实现互操作。在 Go 源码中写入 \texttt{C.foo()} 调用后，Go 编译器会自动生成一个桥接函数，该函数负责数据类型转换并调用真正的 C 函数。值得注意的是，Go 编译器生成的 CGO 桥接函数名并非直接对应源码中的函数名，而是包含哈希后缀，如 \texttt{\_cgo\_8aa400f2462b\_Cfunc\_llama\_decode}，这给符号分析带来了额外困难。

最底层为 llama.cpp C++ 层，这是推理计算的核心所在。\texttt{llama\_decode} 为主循环入口函数，每生成一个 token 均会调用一次，底层通过 ggml 库完成矩阵运算，并通过 mmap、futex、clone3 等系统调用管理内存分配与线程同步。

整个调用路径为：HTTP 请求 $\rightarrow$ Go Handler $\rightarrow$ CGO 桥接函数 $\rightarrow$ llama.cpp 函数 $\rightarrow$ ggml 算子 $\rightarrow$ 内核系统调用。该路径横跨四个不同的运行环境，给完整的调用链追踪带来了挑战。

\subsection{推理引擎面临的安全威胁}

推理引擎的 API 接口是安全事件的高发区域。TorchServe 是 PyTorch 官方提供的模型部署工具，其早期版本在反序列化模型文件时未对输入进行充分校验，攻击者可通过上传特制的 YAML 文件实现任意代码执行，该漏洞被编号为 CVE-2023-43654。

Ollama 框架在 2024 年被安全研究团队发现路径穿越漏洞（CVE-2024-37032，代号 Probllama）。该漏洞的成因是 Ollama API 中的 digest 参数校验不严格，允许攻击者通过路径穿越符（\texttt{../}）访问服务器文件系统中的任意文件。

上述漏洞的共同特征在于：问题的根源位于高层 API 数据处理与底层文件系统访问之间的数据流通路径上。现有安全工具难以还原数据在这一路径上的完整流转过程，因而无法有效支撑此类漏洞的事后分析与溯源。

\section{eBPF 追踪技术}

eBPF（extended Berkeley Packet Filter）是一种运行在内核空间的安全可控的程序执行框架。用户编写的程序经内核 Verifier 检查通过后（验证程序不会出现无限循环或越界访问），由 JIT 编译器编译为本地指令并加载至内核执行，整个过程无需修改内核代码，也无需重启系统。

eBPF 的核心追踪机制包括以下几类。

uprobe 在用户态函数的入口点挂载探针，uretprobe 在函数返回点挂载探针，两者配合可记录函数的执行耗时与调用栈上下文。但需注意，Go 1.17+ 引入的栈管理机制与 uretprobe 的 trampoline 实现存在兼容性问题，在 Go 函数上挂载 uretprobe 可能破坏栈帧结构，导致进程异常。因此，在 Go-CGO-C++ 混合架构中，稳妥的做法是仅在 C/C++ 函数上挂载探针。

tracepoint 在内核预定义的固定位置挂载探针，每个系统调用的入口和返回点均预留了 tracepoint 接口，无需获知函数地址，直接按名称即可 attach。相比 uprobe，tracepoint 的开销更低。

ring buffer 是 eBPF 将数据从内核传回用户态的高效机制，优于早期的 perf buffer，能够在高并发场景下避免数据丢失。

eBPF 的局限在于：其本质上是一种低开销的数据采集手段，不理解被追踪程序的业务语义。eBPF 能够告知"某个系统调用已发生"，但无法说明"该调用对应推理过程的哪个阶段"。这需要结合具体的应用上下文来解读。

\section{跨语言程序静态分析}

多语言混合编程在大型项目中普遍存在。Python 负责高层业务逻辑，C/C++ 实现性能关键路径，Go 构建网络服务，这种组合方式带来了一定的程序分析难度。

不同语言环境之间的控制流在编译后各自独立，Go 层的函数和 C++ 层的函数通过 CGO 桥接函数连接。传统基于单一语言的控制流图（CFG）分析在语言边界处断裂，无法给出完整的跨语言调用路径。

Go 语言调用 C/C++ 代码依靠 CGO 机制。Go 源码中的 \texttt{C.foo()} 调用经编译器处理后，生成一个桥接函数负责数据类型转换与实际函数调用。该桥接函数的命名遵循固定规则，但生成的函数名包含哈希后缀，无法与源码中书写的函数名直接对应。哈希值的生成基于包路径和函数签名，代码的任何改动均会导致哈希值变化，这使得符号表中的 CGO 函数名难以与源码建立可靠关联。

静态符号分析工具（如 \texttt{nm}）能够从编译产物中提取符号列表，但仅能提供符号的存在性信息，无法给出符号之间的调用关系。调用关系需要从源码层面分析，或从运行时调用栈中提取。

部分研究尝试通过统一中间表示来解决跨语言分析问题。POLYCALL 将不同语言编译至 WebAssembly 中间层后统一分析，挖掘出了大量传统方法难以发现的隐藏调用路径，但该方案要求各语言均支持 Wasm 编译目标，实际适用场景有限。

另有研究借助大语言模型来推断跨语言调用关系，绕过人工建立映射规则的低效问题。然而，模型推理生成的函数调用图存在"幻觉"问题，置信度难以达到安全取证场景的要求。

\section{动态二进制插桩}

动态二进制插桩（DBI）技术在程序运行时向其代码段插入额外分析代码，无需源码，也无需重新编译被追踪程序。

DynamoRIO 是具有代表性的 DBI 框架。其核心思想是将待追踪程序的代码复制至"代码缓存"区域，在复制过程中插入分析代码，随后执行修改后的副本。由于代码缓存可重复利用，该方案的性能损耗相较于逐次插桩更低。

Valgrind 的 Memcheck 是另一类 DBI 工具的典型代表。其通过为每个字节的内存访问维护影子内存状态，能够精确检测出未初始化内存使用、越界读写、内存泄漏等问题。然而，影子内存机制的实现代价极高——每次内存访问都需要查询影子表，导致被追踪程序的执行速度下降可达数十倍。

这一性能代价对于推理引擎而言难以承受。以 llama.cpp 在 CPU 上运行 1B 参数模型为例，正常推理每秒可生成数十个 token；若使用 Memcheck 跟踪，生成速度可能降至每秒不足 1 个 token，实时交互体验完全丧失。因此，动态二进制插桩方案不适合作为生产环境中追踪推理引擎的手段。

\section{现有技术的局限性与本文切入点}

综合以上分析，现有技术在追踪多语言推理引擎调用链这一问题上均存在明显不足。

eBPF 能够低开销地采集系统级事件，但本身不具备对 AI 框架内部语义的理解能力；静态符号分析给出的是程序"可能"的运行方式，无法反映"实际"执行路径；动态二进制插桩虽然精度高，但性能代价过大，不适用于推理引擎这类计算密集型程序；跨语言分析工具受限于编译目标或存在置信度问题。

本文的切入点是：将 eBPF 追踪采集运行时事实，与静态符号的语义分类相结合，通过缝合算法生成可理解的跨语言调用链，在不影响推理引擎正常运行的前提下，实现完整调用链的追踪与异常行为分析。下一章将详细阐述 HybriChain 的系统设计方案。

\section{本章小结}

本章介绍了与大模型推理引擎追踪相关的核心技术。大语言模型推理过程中存在内存瓶颈，为解决该问题而引入的各类优化措施使得推理引擎普遍采用多语言混合编程架构，Ollama 即为典型案例。eBPF 技术提供了低开销的系统级追踪能力，但其本身不包含业务语义信息。跨语言程序分析方法各有适用场景与局限，静态分析缺少运行时信息，动态插桩性能代价过高，均无法直接满足推理引擎追踪的需求。下一章将介绍 HybriChain 如何整合上述技术，设计面向推理引擎的跨语言调用链追踪方案。
