\chapter{绪论}
\label{chap:intro}

\section{研究背景与意义}

大语言模型（LLM）这两年火得不行，很多企业和研究机构都选择在本地私有化部署，用开源推理引擎来跑模型。这样做主要是为了数据安全——模型参数和用户数据不出内网，满足合规要求。

开源社区贡献了很多好用的推理引擎。llama.cpp 是纯 C/C++ 写的，轻量高效，能在没有 GPU 的机器上跑；ggml 是它的底层张量库，负责实际的矩阵运算。这两个项目配合起来，可以在普通电脑甚至树莓派上跑几十亿参数的小模型。

但这些推理引擎有个问题：架构太复杂了。

为了解决"大模型参数太多、内存装不下"的问题，开发者搞了很多工程优化。比如 llama.cpp 用整数量化（INT4/INT8）把模型压缩到原来几分之一的大小；PagedAttention 把 KV Cache 分成小 block 来管理，减少内存碎片；有些框架还引入了多级缓存机制，把热点数据放在高带宽内存里。这些优化都是好的，但副作用是代码越来越难懂——一个推理请求进来，数据在 Go 语言层、CGO 桥接层、C++ 计算层、内核层之间来回倒腾了好几遍，安全运维人员根本不知道里面在干什么。

这会带来真实的安全风险。2023 年，PyTorch 的 TorchServe 被发现存在 RCE 漏洞（CVE-2023-43654），攻击者可以通过上传恶意模型文件来执行任意代码。更近一些，Ollama 框架在 2024 年被发现高危漏洞 CVE-2024-37032（Probllama），攻击者可以利用 API 的路径穿越特性读取服务器上的任意文件。这些漏洞有个共同点：它们都和数据在多层语言之间的传递有关，但传统安全工具没办法看清楚数据在内部是怎么流转的。

说白了，现状是这样的：API 层能看到请求进来、响应出去，内核层能看到系统调用，但中间那一段——Go 代码怎么把数据发给 C++、C++ 里哪个函数做了计算、计算过程中有没有访问不该访问的文件——全是黑的。出了安全事件，连"数据从哪进、到哪去"都说不清楚。

所以这篇论文要解决的问题是：怎么把推理引擎内部从 API 请求到内核调用的完整调用链看清楚。

\section{国内外研究现状}

在系统追踪和可观测性这个方向，已经有一些现成的工具。

eBPF 是这几年最火的内核追踪技术。它本质上是一个运行在内核里的虚拟机，可以在不修改程序的情况下插桩观测。传统工具如 strace 靠 ptrace 实现，每次系统调用都要在用户态和内核态之间切换两次，开销很大；eBPF 直接在内核里执行，切换开销低得多。B. Gregg（《Systems Performance》的作者）在 eBPF 推广上做了很多工作，把它的应用从网络扩展到了性能分析领域。

在跨语言程序分析这个方向，学术界想了很多办法把不同语言之间的调用关系拼起来。Go 语言调用 C/C++ 代码用的是 CGO 机制，但 CGO 生成的函数名带哈希后缀，直接看符号表根本认不出来。POLYCALL 项目尝试把不同语言统一转换成 WebAssembly 中间表示来做分析，效果不错，但前提是代码得能用 Wasm 编译——很多实际项目做不到。

还有一些工作是在二进制层面做静态分析，比如从 .so 文件里提取符号表，构建调用图。但静态分析有个根本问题：它只能告诉你程序"可能"怎么跑，告诉你不了程序"实际"怎么跑。推理引擎每次请求走的代码路径可能不一样，光靠静态分析得不到运行时的事实。

动态追踪工具（DBI）如 Valgrind 可以做到很细的内存监控，但代价是性能下降几十倍。对于推理引擎这种每秒处理几十上百 MB 内存吞吐量的程序，用 Valgrind 跟踪几分钟系统就会卡死。

总结一下：现有工具要么开销太大（DBI），要么只能看静态信息（符号分析），要么缺少跨语言语义理解（eBPF 本身只是数据通道，不理解 AI 框架的内部结构）。没有一个工具能同时满足"低开销"、"跨语言"、"有语义"这三个要求。

\section{论文主要工作}

本文围绕"把推理引擎内部的调用链看清楚"这个目标，设计并实现了 HybriChain 系统。

主要做了四件事。

第一，跨语言符号映射。推理引擎里函数符号来自不同语言——Go 的 runtime 函数、CGO 的桥接函数、llama.cpp 的 C++ 函数——名字格式完全不一样。HybriChain 提出了一个八层分类体系，把所有函数按职责分到不同层次（胶水层、API 层、计算层、内存层等），这样调用链上的一条边就变成了"L1 层的函数调用了 L4 层的函数"，语义清晰了。

第二，eBPF 低开销追踪。用 uprobe 在 llama.cpp 的关键函数上挂探针，用 tracepoint 追踪系统调用，在不影响推理引擎正常运行的前提下采集调用数据。相比 strace，eBPF 的性能开销小得多；相比 DBI，不会把程序拖慢几十倍。

第三，动静结合的调用链缝合。静态符号表告诉你程序"有哪些函数"，动态追踪告诉你"哪些函数实际被调用了"。HybriChain 把这两个信息合在一起，给每条调用边打上置信度标签：Confirmed（多次观测到，可以确定）、Inferred（只观测到一边，推测可能是真的）、Unknown（没观测到，可能是没被触发的路径）。

第四，异常行为检测。在缝合后的调用链上跑规则，发现可疑行为：线程同步长时间阻塞（futex 等锁超过 5 秒）、大块内存分配（mmap 超过 1GB）、访问敏感路径（读取 /etc/passwd 等）。

\section{论文组织与结构}

本文共六章。

第 1 章是绪论，说明研究背景（推理引擎架构复杂带来的安全观测盲区）和本文要解决的问题。

第 2 章是相关技术综述，介绍 eBPF、跨语言程序分析、动态二进制插桩等技术的原理和局限性，说明为什么现有方案不够用。

第 3 章是 HybriChain 系统设计，说明整体架构和每个模块的设计思路。

第 4 章是 HybriChain 实现方案，以 Ollama 为具体靶点，说明 bpftrace 脚本怎么写、Python 后处理脚本的关键逻辑、以及每个设计决策的依据。

第 5 章是实验评估，用 TinyLlama-1.1B 和 Qwen2-0.5B 两款模型做实测，评估调用链缝合准确性、系统性能开销、数据压缩效率、以及异常检测能力。

第 6 章是总结与展望。
