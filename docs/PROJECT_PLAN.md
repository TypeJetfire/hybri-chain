## 0. 项目背景与核心问题

### 0.1 研究背景

大语言模型（LLM）正在从云端部署向本地私有化部署快速扩散。Ollama、PyTorch、vLLM 等本地推理框架广泛使用，这些软件涉及大量**核心资产**（模型权重、训练数据、用户 Prompt）的读写，其数据安全问题是网络安全领域的重要课题。

### 0.2 核心痛点（论文切入点）

现代 AI 推理软件普遍采用**混合编程架构**：

```
应用层 (Go/Python)  ──CGO/PyBind11──>  底层库 (C/C++)  ──>  系统调用 (Linux Kernel)
```

这种跨语言边界带来三个核心问题：

1. **语义断层**：调用链在 CGO/PyBind11 边界处断裂，标准静态分析工具无法追踪
2. **API 黑盒**：顶层 RESTful/Python API 屏蔽了底层 read/mmap 等系统调用的实际行为
3. **审计盲区**：现有安全审计工具（IDS/日志审计）只能看到"谁在访问什么文件"，无法还原"从哪个 API 入口触发"

### 0.3 论文核心贡献

提出一套 **"静态符号映射 + eBPF 动态追踪 + 路径缝合算法"** 的方法论，实现：

> **从应用层 API 到底层系统调用的完整调用链还原，覆盖 Go/CGO/C++ 异构代码边界。**

## 1. 研究目标

### 1.1 总体目标

构建一个**可复用的跨语言 API 调用链分析框架**，对多个开源 AI 软件进行系统性数据传输路径审计，生成完整的分层调用树拓扑图。

### 1.2 分解目标

| 编号 | 分目标 | 衡量标准 |
|------|--------|----------|
| G1 | 建立 Go/CGO/C++ 异构符号表映射索引 | 覆盖 Ollama 100% CGO 绑定函数 |
| G2 | 部署 eBPF kprobes 捕获内核系统调用 | 能追踪 open/read/mmap 等 10+ 类系统调用 |
| G3 | 设计路径缝合算法，自动拼接静态链 + 动态轨迹 | 准确率 ≥ 90%（人工验证） |
| G4 | 对 3 个开源软件生成完整调用树 | 每个软件 ≥ 5 棵主要调用树 |
| G5 | 开发可视化看板，展示调用链拓扑 | 支持缩放、点击展开、导出图片 |

## 2. 三个目标软件

| # | 软件 | 语言栈 | 数据传输特征 | 分析优先级 |
|---|------|--------|-------------|-----------|
| 1 | **Ollama** | Go + CGO + C++(llama.cpp) | 模型文件读取（GGUF）、Blob 存储、模板文件 | **P0**（先分析） |
| 2 | **PyTorch** | Python + C++ + CUDA Runtime | 张量序列化、权重加载、DataLoader I/O | **P1**（第二个） |
| 3 | **vLLM** | Python + C++(NCCL/PagedAttention) | KV Cache 内存管理、分布式数据传输 | **P2**（第三个） |

> **为什么选这三个？**
> - Ollama：代表"易用封装层"，跨语言边界最典型（Go↔CGO↔C++），是方法论验证的首选
> - PyTorch：代表"底层框架层"，张量 I/O 路径复杂，涉及 Python→C++ 边界
> - vLLM：代表"高性能推理服务器"，KV Cache 和 NCCL 通信是内存安全的高发区

## 3. 技术路线

### 3.1 总体架构：三层分析

```
┌─────────────────────────────────────────────────────────────────┐
│                    Layer 3: 可视化与验证层                        │
│     调用树渲染 · 交互式浏览 · 导出 PNG/Mermaid · 报告生成           │
├─────────────────────────────────────────────────────────────────┤
│                    Layer 2: 分析与缝合层                          │
│  静态调用链提取  ·  动态轨迹关联  ·  路径缝合算法  ·  差异检测      │
├─────────────────────────────────────────────────────────────────┤
│                    Layer 1: 数据采集层                            │
│   Go AST 分析   ·   CGO 绑定解析   ·   C++ 符号提取   ·   eBPF 追踪 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 分析维度

每个软件从两个维度进行分析：

| 维度 | 说明 | 工具 |
|------|------|------|
| **静态分析** | 从源码构建调用图，不运行程序 | Go AST、Tree-sitter、binutils |
| **动态追踪** | 运行时捕获实际执行路径 | strace、eBPF/bpftrace |

两种方法的结果互相验证、交叉补充。

### 3.3 调用树分层结构

```
L1 应用层 (Application Layer)
    └─ 顶层 API: 如 POST /api/generate, torch.load(), vLLM.generate()

L2 逻辑层 (Business Logic Layer)
    └─ 数据处理: 模型加载、Prompt 分词、张量构建

L3 绑定层 (Binding Layer)
    └─ 跨语言调用: CGO 函数、pybind11、ctypes

L4 底层库层 (Library Layer)
    └─ 标准库/第三方: fopen, mmap, NCCL, cuBLAS

L5 系统调用层 (Syscall Layer)
    └─ Linux Kernel: open, read, pread64, mmap, sendto
```

## 7. 关键决策点

以下问题需要在本规划评审通过后确定：

- [ ] **Q1**: 分析粒度是否聚焦在"文件读取"操作，还是扩展到"网络传输"？
  - 当前规划聚焦文件读取（开题报告已明确），网络传输作为可选扩展
- [ ] **Q2**: PyTorch 分析是否需要覆盖 CUDA/GPU 相关路径？
  - 建议第一版只分析 CPU 路径，GPU 路径作为高级特性
- [ ] **Q3**: vLLM 的 NCCL 分布式传输是否在分析范围内？
  - 建议只分析单机推理路径，分布式训练路径作为扩展
- [ ] **Q4**: 调用树输出格式优先选择 Mermaid 还是自定义 JSON？
  - 建议 JSON 为内部格式，Mermaid 用于文档，D3.js 用于 Web 可视化
